Tổng quan và cách học

Bộ ghi chú về MLOps: đưa mô hình học máy từ notebook thành hệ thống chạy ổn định, tái lập được và được giám sát. Đi từ vòng đời, dữ liệu và đặc trưng, theo dõi thí nghiệm, pipeline, registry, đánh giá, phục vụ, triển khai, giám sát drift, CI/CD/CT, hạ tầng và quản trị.

Đọc trước khi dùng

Đây là ghi chú tự học, tự soạn, không phải tài liệu chính thức của MLflow, Kubeflow, DVC, Feast hay nhà cung cấp nào. Công cụ và API học máy thay đổi nhanh (nhất là MLflow, các nền tảng phục vụ mô hình); ghi chú không tra cứu trực tuyến nên có thể lỗi thời, hãy đối chiếu tài liệu hiện hành và thử trên dữ liệu, mô hình nhỏ trước. Mô hình ảnh hưởng tới quyết định về con người (tín dụng, tuyển dụng, y tế...) cần được đánh giá, kiểm soát và tuân thủ pháp lý kỹ hơn rất nhiều so với nội dung ở đây.

Bạn sẽ làm được gì sau khi học xong

  • Giải thích vì sao đưa mô hình vào sản xuất khó hơn huấn luyện, và MLOps khác DevOps, DataOps ở đâu.
  • Theo dõi thí nghiệm và tái lập kết quả (dữ liệu, mã, tham số, môi trường) bằng MLflow và DVC.
  • Dựng pipeline huấn luyện, registry mô hình và cổng đánh giá trước khi phát hành.
  • Phục vụ mô hình (batch, online), triển khai an toàn (shadow, canary) và giám sát drift.
  • Thiết kế CI/CD/CT cho học máy, kiểm thử dữ liệu và mô hình, và hiểu quản trị mô hình.

Vòng đời học máy và nguyên tắc MLOps

Huấn luyện được một mô hình tốt trong notebook chỉ là phần nhỏ của công việc. MLOps lo phần còn lại: dữ liệu, pipeline, phục vụ, giám sát và vận hành liên tục, vì mô hình hỏng theo cách mà phần mềm thường không hỏng.

Mô hình trong sản xuất khác phần mềm thường

Hệ thống học máy có ba thứ thay đổi thay vì một: mã, dữ liệu và mô hình. Và mô hình có thể suy giảm mà không có thay đổi mã nào, chỉ vì thế giới đổi (hành vi người dùng, mùa vụ, dữ liệu nguồn).

        MÃ (code)  +  DỮ LIỆU (data)  --huấn luyện-->  MÔ HÌNH (model)  --phục vụ-->  DỰ ĐOÁN
            |              |                               |                              |
        phiên bản      phiên bản                       phiên bản                     giám sát: dữ liệu vào,
        trong Git      (DVC, snapshot)                 (registry)                    dự đoán, kết quả thật
     Mỗi kết quả phải truy ngược được tới đúng bộ ba mã + dữ liệu + cấu hình.

Bài báo "Hidden Technical Debt in Machine Learning Systems" chỉ ra phần mã học máy chỉ là hộp nhỏ giữa nhiều thành phần hạ tầng (thu thập dữ liệu, kiểm tra, phục vụ, giám sát...). Nợ kỹ thuật điển hình của ML: mã keo (glue code), "rừng pipeline", phụ thuộc dữ liệu không được khai báo, vòng phản hồi (mô hình ảnh hưởng dữ liệu tương lai của chính nó), nợ cấu hình.

Nguyên tắc cốt lõi

  1. Tái lập được: cùng mã, dữ liệu, cấu hình, môi trường cho cùng kết quả (hoặc sai khác giải thích được).
  2. Phiên bản hoá mọi thứ: mã, dữ liệu, tham số, mô hình, môi trường.
  3. Tự động hoá pipeline từ dữ liệu tới triển khai; thủ công chỉ ở nơi có chủ đích (duyệt).
  4. Kiểm thử cả dữ liệu và mô hình, không chỉ mã.
  5. Một đường cho huấn luyện và phục vụ: dùng cùng mã đặc trưng để tránh lệch.
  6. Giám sát liên tục dữ liệu và dự đoán; mô hình suy giảm lặng lẽ.
  7. Phát hành dần và quay lui được như mọi hệ thống sản xuất (Chiến lược triển khai).
  8. Trách nhiệm và minh bạch: tài liệu mô hình, kiểm soát thiên lệch, nhật ký kiểm toán (Quản trị).
  9. Bắt đầu đơn giản: mô hình đơn giản trong hệ thống tốt thắng mô hình phức tạp trong hệ thống tệ; thường nên có đường cơ sở dễ (quy tắc, hồi quy logistic).

Dữ liệu và đặc trưng cho học máy

Dữ liệu và đặc trưng quyết định chất lượng mô hình nhiều hơn thuật toán. Hai nguy cơ lớn nhất không nằm ở mô hình: rò rỉ dữ liệu và lệch giữa huấn luyện với phục vụ.

Phiên bản hoá dữ liệu

Mã nằm trong Git, nhưng dữ liệu quá lớn cho Git. Cần cách gắn đúng phiên bản dữ liệu với đúng commit mã và mô hình.

DVC (Data Version Control) lưu con trỏ nhỏ trong Git và dữ liệu thật ở kho từ xa (S3, GCS, SSH...):

git init && dvc init
dvc add data/train.csv                  # tạo data/train.csv.dvc (con trỏ, commit vào Git) và bỏ tệp lớn khỏi Git
git add data/train.csv.dvc data/.gitignore && git commit -m "thêm dữ liệu huấn luyện v1"
dvc remote add -d storage s3://my-bucket/dvc
dvc push                                 # đẩy dữ liệu lên kho từ xa
# ở máy khác, hoặc commit cũ:
git checkout <commit> && dvc pull        # lấy đúng dữ liệu của commit đó

Các cách khác: bảng có time travel (Delta, Iceberg: truy vấn bảng tại một thời điểm), snapshot bất biến trong object storage với đường dẫn có phiên bản, hoặc lưu mã băm dữ liệu cùng thí nghiệm. Quy tắc chung: mỗi mô hình phải truy ngược được tới đúng dữ liệu đã huấn luyện nó.

Kiểm tra dữ liệu trước khi huấn luyện

Huấn luyện trên dữ liệu xấu cho mô hình xấu mà không báo lỗi. Kiểm tra tự động trước mỗi lần huấn luyện:

Rò rỉ dữ liệu (data leakage) là khi thông tin từ tương lai hoặc từ tập kiểm thử lọt vào huấn luyện, làm điểm đánh giá đẹp giả tạo rồi sụp đổ khi triển khai. Các dạng phổ biến:

  • Rò rỉ theo thời gian: chia ngẫu nhiên dữ liệu chuỗi thời gian, để mô hình "nhìn thấy tương lai". Với dữ liệu thời gian phải chia theo thời gian (huấn luyện trên quá khứ, kiểm thử trên tương lai).
  • Đặc trưng chứa đáp án: đặc trưng chỉ có sau khi biết nhãn (ví dụ "số lần gọi hỗ trợ chấm dứt hợp đồng" khi dự đoán khách rời bỏ).
  • Tiền xử lý trên toàn bộ dữ liệu: chuẩn hoá hoặc điền thiếu bằng thống kê tính trên cả tập kiểm thử. Phải fit trên train, rồi áp dụng cho validation/test.
  • Trùng giữa các tập: cùng một người/đối tượng xuất hiện ở cả hai tập.
from sklearn.pipeline import make_pipeline

Lệch giữa huấn luyện và phục vụ (training-serving skew)

Đây là nguyên nhân hàng đầu khiến mô hình tốt ngoại tuyến lại kém khi chạy thật: đặc trưng được tính khác nhau ở hai nơi (huấn luyện bằng SQL/pandas trên kho, phục vụ bằng mã khác trong dịch vụ). Giải pháp:

  • Một định nghĩa đặc trưng, dùng ở cả hai nơi: đóng gói tiền xử lý vào chính mô hình (pipeline), hoặc dùng feature store.
  • Kiểm tra bằng cách ghi lại đặc trưng thật lúc phục vụ rồi so với đặc trưng tính ngoại tuyến cho cùng thực thể.
  • Kiểm thử tương đương: cùng đầu vào cho cùng đặc trưng ở hai đường.

Gán nhãn và chất lượng nhãn

  • Nhãn sai làm trần chất lượng của mô hình. Đo độ đồng thuận giữa người gán nhãn, rà soát mẫu.
  • Nhãn đến trễ (khách rời bỏ biết sau 3 tháng): ảnh hưởng cách đánh giá và giám sát (Giám sát).
  • Vòng phản hồi: nhãn có thể bị ảnh hưởng bởi chính mô hình (chỉ biết kết quả của người được duyệt vay).
Rò rỉ do chọn đặc trưng trên toàn bộ dữ liệu
python3 - <<'EOF'
import numpy as np
from sklearn.feature_selection import SelectKBest, f_classif
from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import cross_val_score
from sklearn.pipeline import make_pipeline

rng = np.random.default_rng(0)
X = rng.normal(size=(100, 2000))          # 2000 đặc trưng HOÀN TOÀN là nhiễu
y = rng.integers(0, 2, size=100)          # nhãn ngẫu nhiên: không có gì để học, điểm đúng phải gần 0,5

# SAI: chọn 20 đặc trưng "tốt nhất" bằng TOÀN BỘ dữ liệu (kể cả phần sẽ dùng để kiểm thử), rồi mới cross-validate
X_leak = SelectKBest(f_classif, k=20).fit_transform(X, y)
leak = cross_val_score(LogisticRegression(max_iter=1000), X_leak, y, cv=5).mean()

# ĐÚNG: việc chọn đặc trưng nằm TRONG pipeline, nên chỉ fit trên phần train của từng fold
pipe = make_pipeline(SelectKBest(f_classif, k=20), LogisticRegression(max_iter=1000))
good = cross_val_score(pipe, X, y, cv=5).mean()

print("rò rỉ (SAI) :", round(leak, 3), " <- đẹp một cách vô lý trên dữ liệu ngẫu nhiên")
print("pipeline (ĐÚNG):", round(good, 3), " <- gần mức ngẫu nhiên (0,5; dao động theo mẫu)")

Model registry

Model registry là kho trung tâm quản lý các phiên bản mô hình: ai huấn luyện, từ dữ liệu nào, chỉ số ra sao, đang ở giai đoạn nào, và bản nào đang chạy ở production. Nó biến "tệp mô hình trong thư mục" thành tài sản có kiểm soát.

Vì sao cần

Không có registry, câu hỏi cơ bản không trả lời được: mô hình đang chạy ở production là bản nào? huấn luyện từ đâu? có thể quay về bản trước không? Mô hình bị lưu rải rác (model_final_v2_ok.pkl), không ai chắc cái nào đang được dùng.

Đánh giá mô hình và cổng chất lượng

Đánh giá quyết định mô hình có được phát hành hay không. Chỉ số tổng thể một con số thường che giấu những chỗ mô hình tệ; cần đánh giá theo lát cắt, so với đường cơ sở và mô hình hiện tại, và kiểm thử hành vi.

Chọn chỉ số đúng bài toán

Phân loại lệch lớp (gian lận, bệnh hiếm)Precision, recall, PR-AUC, F199% accuracy có thể là mô hình luôn đoán "không gian lận"

Chỉ số kỹ thuật phải gắn với chỉ số nghiệp vụ: precision/recall được chuyển thành chi phí (mỗi cảnh báo giả tốn bao nhiêu, mỗi ca bỏ sót tốn bao nhiêu), và ngưỡng quyết định được chọn theo chi phí đó chứ không mặc định 0,5.

Đường cơ sở và so sánh

  • Đường cơ sở đơn giản (luôn đoán lớp phổ biến, hồi quy logistic, quy tắc nghiệp vụ): mô hình phức tạp phải thắng nó rõ rệt mới đáng.
  • So với mô hình hiện tại ("champion") trên cùng tập đánh giá: mô hình mới tốt hơn thật hay chỉ nhiễu?
  • Khoảng tin cậy: so sánh sai khác với độ dao động (nhiều hạt giống, bootstrap), không chỉ hai con số.

Cổng chất lượng trước khi đăng ký

Mô hình mới chỉ đi tiếp nếu đạt mọi điều kiện:

def quality_gate(new, champion, min_auc=0.75, max_drop=0.005):
    checks = {
        "AUC tối thiểu":            new["auc"] >= min_auc,
        "Không tệ hơn champion":    new["auc"] >= champion["auc"] - max_drop,
        "Lát cắt yếu nhất đủ":      new["worst_slice_auc"] >= 0.70,
        "Độ trễ dự đoán đạt":       new["p95_latency_ms"] <= 50,
        "Kiểm thử hành vi qua":     new["behavior_tests_passed"],
    }
    failed = [k for k, ok in checks.items() if not ok]
    return (not failed), failed

  • Ngưỡng cần có lý do (từ yêu cầu nghiệp vụ), không tuỳ ý.
  • Thất bại thì dừng và báo, không tự động triển khai.
  • Ghi kết quả cổng vào registry (thẻ) để kiểm toán.

Đánh giá ngoại tuyến và trực tuyến

Chỉ số ngoại tuyến (trên dữ liệu lịch sử) là đại diện cho hiệu quả thật, không phải bản thân nó. Mô hình tốt ngoại tuyến vẫn có thể không cải thiện chỉ số kinh doanh. Xác nhận bằng thí nghiệm trực tuyến (A/B, canary) trước khi coi là thành công (Chiến lược triển khai).

Cổng chất lượng với đánh giá theo lát cắt

import numpy as np, pandas as pd
from sklearn.datasets import make_classification
from sklearn.model_selection import train_test_split
from sklearn.linear_model import LogisticRegression
from sklearn.ensemble import RandomForestClassifier
from sklearn.metrics import roc_auc_score

X, y = make_classification(n_samples=4000, n_features=15, n_informative=6, random_state=3)
region = np.random.RandomState(3).choice(["A", "B", "C"], size=len(y), p=[0.6, 0.3, 0.1])
Xtr, Xte, ytr, yte, rtr, rte = train_test_split(X, y, region, test_size=0.3, random_state=3)

champion = LogisticRegression(max_iter=1000).fit(Xtr, ytr)
challenger = RandomForestClassifier(n_estimators=150, random_state=3).fit(Xtr, ytr)

def report(m):
    s = m.predict_proba(Xte)[:, 1]
    out = {"auc": roc_auc_score(yte, s)}
    out["worst_slice_auc"] = min(roc_auc_score(yte[rte == r], s[rte == r]) for r in "ABC")
    return out

c, n = report(champion), report(challenger)
print("champion  :", {k: round(v, 3) for k, v in c.items()})
print("challenger:", {k: round(v, 3) for k, v in n.items()})
checks = {"AUC >= 0.75": n["auc"] >= 0.75, "không tệ hơn champion": n["auc"] >= c["auc"] - 0.005, "lát cắt yếu nhất >= 0.70": n["worst_slice_auc"] >= 0.70}
print(checks, "->", "ĐI TIẾP" if all(checks.values()) else "DỪNG")

import joblib
import numpy as np
from fastapi import FastAPI
from pydantic import BaseModel, Field

app = FastAPI()
model = joblib.load("model.joblib")                # tải một lần lúc khởi động, không tải mỗi yêu cầu

    f0: float
    f1: float
    f2: float
    tenure_months: int = Field(ge=0, le=600)       # kiểm tra đầu vào: từ chối giá trị vô lý

@app.get("/healthz")
def health():
    return {"status": "ok"}

@app.post("/predict")
def predict(x: Features):
    row = np.array([[x.f0, x.f1, x.f2, x.tenure_months]])
    p = float(model.predict_proba(row)[0, 1])
    return {"churn_probability": p, "model_version": "1"}

  • Giới hạn thời gian và tài nguyên; dự đoán mất quá lâu thì có phương án dự phòng (giá trị mặc định, quy tắc đơn giản).

Chiến lược triển khai mô hình

Mô hình mới tốt ngoại tuyến chưa chắc tốt ở production. Triển khai dần với quan sát giúp biết chắc, và quay lui nhanh khi không như mong đợi.

Vì sao khác triển khai phần mềm thường

  • Lỗi của mô hình không gây lỗi (không ngoại lệ, không mã 500): chỉ là dự đoán kém mà không ai thấy ngay.
  • Chất lượng phụ thuộc dữ liệu thật, không kiểm thử đầy đủ được trước.
  • Nhãn đúng thường đến trễ, nên phản hồi chậm.

Vì vậy triển khai mô hình cần chiến lược quan sát trước, quyết định sau, với chỉ số rõ ràng.

Quy tắc canary: định ngưỡng dừng và quay lui tự động trước (Progressive delivery). Với mô hình, chỉ số nghiệp vụ thường quan trọng hơn chỉ số kỹ thuật vì mô hình có thể chạy hoàn hảo về kỹ thuật mà dự đoán tệ.

A/B test mô hình: cẩn thận về thống kê

  • Chia ngẫu nhiên theo đơn vị đúng (người dùng, không phải yêu cầu) để một người luôn thấy cùng một bản.
  • Định kích thước mẫu và thời gian trước, đừng "nhìn lén" kết quả rồi dừng khi thấy đẹp (tăng tỷ lệ kết luận sai).
  • Một chỉ số chính quyết định, các chỉ số phụ để quan sát.
  • Chú ý hiệu ứng mới lạ (người dùng phản ứng khác với thứ mới) và tính mùa vụ.
  • Thí nghiệm có thể ảnh hưởng lẫn nhau nếu chạy nhiều cái cùng lúc trên cùng người dùng.

Triển khai và quay lui

  • Triển khai là đổi con trỏ (bí danh trong registry, trọng số trong router), nên quay lui nhanh (Registry).
  • Giữ phiên bản cũ luôn sẵn sàng phục vụ.
  • Đặt phiên bản mô hình và phiên bản mã/đặc trưng cùng nhau: mô hình mới có thể cần đặc trưng mới; hai thứ phải triển khai tương thích (Chiến lược phát hành).
  • Cho phương án dự phòng (fallback): khi mô hình lỗi hoặc quá chậm, dùng quy tắc đơn giản thay vì làm hỏng dịch vụ.
  • Với mô hình học liên tục, cẩn thận vòng phản hồi: mô hình ảnh hưởng dữ liệu về sau của chính nó.
Mô phỏng shadow so sánh hai mô hình
python3 - <<'EOF'
import numpy as np
from sklearn.datasets import make_classification
from sklearn.model_selection import train_test_split
from sklearn.linear_model import LogisticRegression
from sklearn.ensemble import GradientBoostingClassifier
X, y = make_classification(n_samples=6000, n_features=12, n_informative=5, random_state=5)
Xtr, Xlive, ytr, ylive = train_test_split(X, y, test_size=0.5, random_state=5)
champion = LogisticRegression(max_iter=1000).fit(Xtr, ytr)
challenger = GradientBoostingClassifier(random_state=5).fit(Xtr, ytr)

# "traffic thật": cả hai dự đoán; chỉ champion trả về người dùng
pc, pn = champion.predict_proba(Xlive)[:, 1], challenger.predict_proba(Xlive)[:, 1]
agree = np.mean((pc > 0.5) == (pn > 0.5))
print("tỷ lệ đồng thuận quyết định:", round(agree, 3))
print("điểm trung bình champion/challenger:", round(pc.mean(), 3), round(pn.mean(), 3))
# nhãn đến trễ: sau đó mới so sánh chất lượng
from sklearn.metrics import roc_auc_score
print("AUC khi nhãn về: champion", round(roc_auc_score(ylive, pc), 3), "challenger", round(roc_auc_score(ylive, pn), 3))
EOF

Giám sát và phát hiện drift

Mô hình suy giảm mà không báo lỗi. Giám sát học máy nhìn vào dữ liệu vào, dự đoán và (khi có) kết quả thật, để phát hiện suy giảm trước khi người dùng phát hiện.

import numpy as np

def psi(expected, actual, bins=10):
    edges = np.quantile(expected, np.linspace(0, 1, bins + 1))
    edges[0], edges[-1] = -np.inf, np.inf
    e = np.histogram(expected, edges)[0] / len(expected)
    a = np.histogram(actual, edges)[0] / len(actual)
    e, a = np.clip(e, 1e-6, None), np.clip(a, 1e-6, None)        # tránh chia cho 0
    return float(np.sum((a - e) * np.log(a / e)))

Các ngưỡng là quy ước kinh nghiệm, không phải quy luật: hiệu chỉnh theo từng đặc trưng và theo tác động lên mô hình. Drift trong một đặc trưng không quan trọng với mô hình thì không đáng báo động; ưu tiên đặc trưng có tầm quan trọng cao.

Công cụ: Evidently, WhyLabs/whylogs, NannyML, các tính năng giám sát của SageMaker, Vertex AI, Arize, Fiddler.

Phát hiện drift bằng PSI và KS
python3 - <<'EOF'
import numpy as np
from scipy.stats import ks_2samp

def psi(expected, actual, bins=10):
    edges = np.quantile(expected, np.linspace(0, 1, bins + 1)); edges[0], edges[-1] = -np.inf, np.inf
    e = np.clip(np.histogram(expected, edges)[0] / len(expected), 1e-6, None)
    a = np.clip(np.histogram(actual, edges)[0] / len(actual), 1e-6, None)
    return float(np.sum((a - e) * np.log(a / e)))

rng = np.random.default_rng(0)
train = rng.normal(40, 10, 20000)                 # tuổi lúc huấn luyện
stable = rng.normal(40, 10, 5000)                 # tuần này, không đổi
drifted = rng.normal(46, 12, 5000)                # tuần này, người dùng già hơn và phân tán hơn
broken = np.where(rng.random(5000) < 0.3, np.nan, rng.normal(40, 10, 5000))   # 30% thiếu (lỗi pipeline)

print("PSI ổn định :", round(psi(train, stable), 4))
print("PSI drift   :", round(psi(train, drifted), 4))
print("KS drift p  :", ks_2samp(train, drifted).pvalue)
print("tỷ lệ NULL ở dữ liệu lỗi:", round(float(np.isnan(broken).mean()), 3), "<- bắt bằng kiểm tra chất lượng, không phải PSI")
EOF

CI/CD/CT và kiểm thử học máy

Hệ thống học máy cần ba vòng tự động hoá: CI kiểm tra mã và dữ liệu, CD triển khai mô hình và dịch vụ, và CT (huấn luyện liên tục) làm mới mô hình khi dữ liệu thay đổi. Kèm theo là bộ kiểm thử riêng cho dữ liệu và mô hình.

Hạ tầng, GPU và chi phí

Học máy tiêu tốn tài nguyên theo cách khác dịch vụ web: huấn luyện nặng và gián đoạn, suy luận cần phần cứng đặc biệt. Quản lý hạ tầng và chi phí tốt quyết định dự án có bền vững không.

GPU trên Kubernetes

Kubernetes quản lý GPU qua device plugin (ví dụ của NVIDIA), khai báo như một loại tài nguyên:

  containers:
    - name: train
      image: registry.example.com/ml/train:1.2.0
      resources:
        limits:
          nvidia.com/gpu: 1            # GPU chỉ khai báo trong limits, và là số nguyên
          memory: 32Gi
        requests:
          cpu: "8"
          memory: 32Gi
  • GPU thường không chia nhỏ mặc định (một Pod một GPU nguyên); có kỹ thuật chia sẻ (time-slicing, MIG) với đánh đổi riêng.
  • Đặt taint cho node GPU và toleration cho Pod cần GPU để workload thường không chiếm máy đắt tiền (Scheduling).
  • Job cho huấn luyện (chạy xong là giải phóng), Deployment cho phục vụ (Job, CronJob).
  • Đặt requests và limits bộ nhớ hợp lý để tránh OOM giữa chừng (Tài nguyên).

Quản trị mô hình và học máy có trách nhiệm

Mô hình đưa ra quyết định ảnh hưởng đến con người. Quản trị bảo đảm mô hình được ghi chép, kiểm soát, giám sát về thiên lệch, và có người chịu trách nhiệm khi nó sai.

Đây không phải tư vấn pháp lý

Quy định về AI và dữ liệu (như đạo luật AI của EU phân loại theo mức rủi ro, các luật bảo vệ dữ liệu cá nhân) đang phát triển và khác nhau theo khu vực và lĩnh vực. Nội dung dưới đây là khung kỹ thuật và quy trình tham khảo; hãy làm việc với bộ phận pháp lý, tuân thủ và rủi ro của tổ chức cho yêu cầu cụ thể.

  • Đo chỉ số theo nhóm (nếu phù hợp pháp lý và đạo đức) và theo dõi theo thời gian (Đánh giá).

  • Giảm thiểu dữ liệu thu thập; che và ẩn danh sớm (Quản trị dữ liệu).
  • Mô hình có thể ghi nhớ dữ liệu huấn luyện (đặc biệt mô hình lớn); cẩn thận với dữ liệu cá nhân trong tập huấn luyện và đầu ra.

  • Kiểm soát truy cập vào dữ liệu và mô hình.

Kiểm toán và truy vết

Với mỗi dự đoán quan trọng cần có thể trả lời: phiên bản mô hình nào, đặc trưng đầu vào nào, vào lúc nào, ai/hệ thống nào dùng kết quả. Điều này cần:

  • Registry với lineage đầy đủ (Registry).
  • Log dự đoán có kiểm soát (Giám sát).
  • Nhật ký thay đổi: ai đã nâng bản nào lên production và dựa trên cổng nào.

Viết model card và kế hoạch giám sát cho mô hình của bạn

Chọn một mô hình thật hoặc giả định, viết một model card theo mẫu trên (dưới 20 dòng). Rồi trả lời:

  1. Có ai bị ảnh hưởng nặng nếu mô hình sai không, và mô hình thuộc mức rủi ro nào?
  2. Bạn đo hiệu năng theo lát cắt nào, và ngưỡng tối thiểu của lát cắt yếu nhất là gì?
  3. Ai được nâng mô hình lên production, dựa trên cổng nào, và ghi ở đâu?
  4. Nếu một khách hàng hỏi "vì sao tôi bị từ chối", bạn có trả lời được không, và bằng cách nào?
  5. Dữ liệu cá nhân nào nằm trong tập huấn luyện, và quy trình khi có yêu cầu xoá là gì?

Dự án mẫu cục bộ: huấn luyện, đăng ký, phục vụ, giám sát

Một vòng MLOps nhỏ chạy trên máy bạn: huấn luyện nhiều mô hình với MLflow, cổng đánh giá, đăng ký champion, phục vụ qua FastAPI, rồi mô phỏng drift và phát hiện nó. CPU, không cần cloud.

Mục tiêu

Đi qua gần đủ vòng đời: dữ liệu → thí nghiệm → cổng → registry → phục vụ → giám sát, với mô hình nhỏ để chạy trong vài giây.

Bước 2: Thí nghiệm, cổng chất lượng và đăng ký champion

cat > train.py <<'EOF'
import mlflow, mlflow.sklearn, pandas as pd, numpy as np, json
from mlflow import MlflowClient
from sklearn.model_selection import train_test_split
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.linear_model import LogisticRegression
from sklearn.ensemble import GradientBoostingClassifier
from sklearn.metrics import roc_auc_score

mlflow.set_tracking_uri("sqlite:///mlflow.db"); mlflow.set_experiment("churn")
df = pd.read_csv("train.csv"); X, y = df.drop(columns="churn"), df["churn"]
Xtr, Xte, ytr, yte = train_test_split(X, y, test_size=0.3, random_state=0, stratify=y)

candidates = {
    "logreg": make_pipeline(StandardScaler(), LogisticRegression(max_iter=1000)),
    "gbm": GradientBoostingClassifier(random_state=0),
}
best = None
for name, model in candidates.items():
    with mlflow.start_run(run_name=name) as run:
        model.fit(Xtr, ytr)
        auc = roc_auc_score(yte, model.predict_proba(Xte)[:, 1])
        mlflow.log_param("model", name); mlflow.log_metric("test_auc", auc)
        mlflow.set_tag("data_version", "train.csv-v1")
        mlflow.sklearn.log_model(model, "model", serialization_format="cloudpickle")   # xem ghi chú bên dưới
        print(f"{name}: AUC={auc:.4f}")
        if best is None or auc > best[1]: best = (run.info.run_id, auc, name)

run_id, auc, name = best
client = MlflowClient()
GATE_MIN_AUC = 0.60
if auc < GATE_MIN_AUC:
    raise SystemExit(f"CỔNG: AUC {auc:.3f} < {GATE_MIN_AUC}, dừng, không đăng ký")
mv = mlflow.register_model(f"runs:/{run_id}/model", "churn-model")
client.set_registered_model_alias("churn-model", "champion", mv.version)
json.dump({"auc": auc, "model": name}, open("champion_metrics.json", "w"))
print("đã đăng ký", name, "phiên bản", mv.version, "thành champion")
EOF
python3 train.py
Về định dạng lưu mô hình sklearn của MLflow

Các bản MLflow mới có thể mặc định lưu mô hình scikit-learn bằng định dạng skops (an toàn hơn pickle) và từ chối loại "không tin cậy", trong đó có các mô hình cây (Random Forest, Gradient Boosting): log_model báo lỗi "untrusted types" trừ khi bạn khai báo rõ danh sách kiểu tin cậy (skops_trusted_types) sau khi đã xem xét. Trong lab này mô hình do chính bạn huấn luyện nên dùng serialization_format="cloudpickle" cho gọn. Với mô hình đến từ nguồn bên ngoài, hãy làm ngược lại: giữ định dạng an toàn, chỉ tin các kiểu bạn đã kiểm tra (Registry, Phục vụ). Tên tham số và mặc định thay đổi theo phiên bản MLflow: đối chiếu tài liệu.

import mlflow, pandas as pd
from fastapi import FastAPI
from pydantic import BaseModel, Field
mlflow.set_tracking_uri("sqlite:///mlflow.db")
model = mlflow.sklearn.load_model("models:/churn-model@champion")
app = FastAPI()
class Customer(BaseModel):
    tenure_months: int = Field(ge=0, le=600)
    monthly_spend: float = Field(ge=0)
    support_calls: int = Field(ge=0)
@app.get("/healthz")
def health(): return {"status": "ok"}
@app.post("/predict")
def predict(c: Customer):
    p = float(model.predict_proba(pd.DataFrame([c.model_dump()]))[0, 1])
    return {"churn_probability": round(p, 4)}

Bước 4: Giám sát drift

cat > monitor.py <<'EOF'
import numpy as np, pandas as pd
from scipy.stats import ks_2samp

def psi(expected, actual, bins=10):
    edges = np.quantile(expected, np.linspace(0, 1, bins + 1)); edges[0], edges[-1] = -np.inf, np.inf
    e = np.clip(np.histogram(expected, edges)[0] / len(expected), 1e-6, None)
    a = np.clip(np.histogram(actual, edges)[0] / len(actual), 1e-6, None)
    return float(np.sum((a - e) * np.log(a / e)))

ref = pd.read_csv("train.csv")
rng = np.random.default_rng(99)
live = pd.DataFrame({                                       # "tuần này": nhiều khách mới và gọi hỗ trợ nhiều hơn
    "tenure_months": rng.integers(1, 20, 2000),
    "monthly_spend": rng.normal(62, 20, 2000).clip(5),
    "support_calls": rng.poisson(3.0, 2000),
})
for col in ["tenure_months", "monthly_spend", "support_calls"]:
    v = psi(ref[col].values, live[col].values)
    status = "ỔN ĐỊNH" if v < 0.1 else ("THAY ĐỔI VỪA" if v < 0.25 else "DRIFT ĐÁNG KỂ")
    print(f"{col:15s} PSI={v:.3f}  {status}")
EOF
